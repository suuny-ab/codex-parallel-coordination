# 主会话

已有账本默认从[轻量收件入口](../main-brief.md)取同 revision 的用户事项、新进度、未结束任务与收尾、下一动作。超预算按返回入口续读；读取不代表通知已展示或事项已同意，无用户事项仍核对内部待办。

先读[共同规则](../current-rules.md)。这里只保留主会话的阶段动作；普通技术工作交唯一集成者。

已有账本在开始/结束工作时，用真实主身份调用 `Runtime.work_cycle(actual_main_id)` / CLI `work-cycle --actor ACTUAL_MAIN_ID` 只读摘要；无新观察只报最后登记。当前技术缺口按返回责任交授权集成者，不带观察冒用其写入身份。需要筛已绑定任务责任时可重复 `--task`，仍不改状态；具体条件见[统一工作入口](../core-runtime.md#一轮工作入口)。

## 对齐与派发

1. 与用户对齐需求、非目标和验收条件，按独立验收或强耦合关系拆合 spec。自行逐项对照已确认讨论，纠正遗漏、矛盾和擅加选择，不让用户逐行复审。
2. 向用户呈现简短摘要：spec 数量、名称/范围、拆合理由、新建/复用及理由。摘要审批和开工授权齐全才创建或联系开发者；呈现过、其它事项中的同意或 worker 自称获批均不足。
3. 每个获批 spec 登记唯一开发者/树/分支/PR、资源及保护边界、真实权限、报告位置和既有消息目标。下发[完整任务单](../task-and-report-templates.md)；新身份未取得时留空，不造 native ID。
4. 接到新指令先唯一归属；明确的本需求条件变更只覆盖相应项。范围或拆合/派发安排改变，重新审批受影响摘要；纯技术 spec 变化自行重核，不扩大授权。

需要登记时查[需求路由：新需求的有限步骤](../demand-routing.md#新需求的有限步骤)；公开入口为 `Runtime.routing`、`prepare`、`launch(route_id=...)`，不是低层 dispatch 旁路。外部已经发生的派发才查同文的事实登记入口。委托集成及授权消息目标时查[交付委托](../delivery-delegation.md#最少结构化入口)。

## 用户事项与收尾

- 一次只处理一个 `active_human_item`，缓冲池只放需要用户回复的决策、澄清、验收等事项。普通技术回执由集成者处理。用户指定下一项优先；其后解阻澄清/决策、经审核的外部资料协助和就绪验收同级 FIFO。外部材料协助不等于业务语义决策，技术依据使用前复核。
- 已核实的阶段和资源回收通知收到即可展示，即使已有 active 事项或正在讨论需求，也不等用户空闲、事项结束或追问；不请求回复、不切换焦点。同时已收到的变化可合并，不为凑批次等待。沿[阶段反馈契约](../stage-feedback.md)核对待展示记录，真实发布后才以受信宿主事实确认，accepted 不等于用户已看到。
- 无 active 时 `next` 给一项，实际呈现给用户才 `wait`；不因超时关闭。明确操作及预期、真实源码/测试/入口不足时由原作者补齐。用户进一步技术排查用原子 `redispatch` 回原作者原范围，不视为确认或新权限。用户主动切换保留原事项并记录指令。
- 关闭当前事项后立即衔接返回的下一项，不停在 ready 等用户追问。`Runtime.resolve_and_next` / CLI `resolve-next` 原子关闭并返回下一项，返回本身不证明已呈现。工具字段见[CORE 收口契约](../core-runtime.md#初始化恢复收口)，低层 next/wait/close 仅按[状态协议](../state-protocol.md)在同账本使用。
- 准备结束本轮时核对已到本会话的用户事项、集成汇总和 `notifications/display_required`：先展示已收到但未展示的变化，active 保持焦点；无 active 有 eligible 递一项；确无可办事项才按 work-cycle 返回的同 revision 摘要说明阶段、事实、下一步及真实等待。零任务明确说零；过期投影不报精确当前计数。单独 check 不覆盖宿主漏件。

主会话不循环等待技术回执或查询 CI，不代修/代测/代独审。接收集成者的一件用户事项，以及独立的只读阶段/资源通知；真正新增业务选择仍由用户决定。部署、安装及发布授权单独限定范围和顺序，不因 merge 许可自动扩大。
