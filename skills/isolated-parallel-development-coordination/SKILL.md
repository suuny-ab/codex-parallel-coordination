# 隔离并行开发协调

用户只在原主会话讨论需求、作业务决策和验收，授权范围及顺序。单一交付 agent 负责技术独审、CI 跟进、直接对接原作者、唯一串行合 main，以及独立明确授权内的 tag/备份/部署/发布核验。普通技术事件在交付侧闭环，不让主会话循环 wait、查 CI/日志或逐步接力。代码需求由唯一原作者在隔离 worktree 实现、自测、同步最新 main、处理冲突/功能问题、集成回归并维护同一个 MR；交付者不代修业务。没有实际联系/收件能力时记录一次具体通路例外，不创建替代用户对话。

主会话先完成业务对齐，再按独立验收或强耦合关系拆合 spec，自行逐项对照已确认讨论纠正遗漏、矛盾或擅加选择。用户审批简明摘要中的 spec 数量、名称范围、拆合理由、新建/复用及理由；不能把呈现摘要、其它事项中的同意或 worker 自称获批当审批，也不要求用户逐行复审 spec。批准及开工授权齐全才创建或联系开发者。每个获批 spec 对应一需求、一开发 agent、一工作树和一个 PR；不把空闲或熟悉模块当复用依据。查询、解释、只读分析与 spec 比对由主会话承担，不新建只读开发或独立审核 agent。

每条指令先唯一归属需求，多个要求分别处理；模糊部分单独暂存，其它任务继续。新指令仅覆盖本需求明确改变的条件，其余限制继续有效。范围内补充及缺陷回原未结束需求；验收后冻结范围，只有原目标缺陷回原 PR，新能力另立需求。开发者提出跨任务依赖时给出目标任务、依赖约定、实际变化、最小动作；集成核实双方范围后加入目标任务待办，不自动中断、重排或广播，传到第三任务重新核实。工具检查结构、身份、版本和授权，语义归属仍由主会话判断。见 [需求收口与路由入口](references/demand-routing.md)。

代码任务合 main 并核对后才完成；只读任务按下文合法成果核验入口结束，明确需要用户验收的仍等用户通过。开发交付、技术测试、业务质量、功能验收、集成、审核、合入和部署分开。派工可以记录用户已明确给予本任务的 commit/push/MR/merge 权限，工具不能赋权。默认全部拒绝；既有批次限制不因使用本机制解除。部署需要独立范围授权。

## 工作入口

首版公开入口为 Python 3.11+ 标准库工具 `scripts/core_runtime.py`，先读[CORE 接口](references/core-runtime.md)。state-root 由受信插件 profile 固定，按规范化项目根路径派生唯一账本；报告只是指纹证据，不另存任务队列。原 `scripts/coordination.py` 及[状态协议](references/state-protocol.md)保留离线诊断/兼容，不能另建并行生产账本。Windows 核实解释器，命令加 `-B`；项目参数不写入通用 skill。

1. 确认范围、非目标、验收条件、用户开工指令、资源归属及保护边界，通过 `Runtime.routing` 保存讨论/spec核对、摘要与用户审批、指令归属和限定动作；`prepare` 排队，`launch(route_id=...)` 在调用宿主前重验当前依据。资源准入及宿主实际运行观察齐全才记 running；发送接受不代表运行或交付，spawn 满额即时给真实排队原因，不自动关闭执行者。外部已经发生的真实派发用 `bind_observed_dispatch` 核原批准及当前观察后登记，不伪造 launch、准入或完成。工作 agent 自行准备隔离工作树、数据副本、端口、缓存；共享资源只读复用，重型任务遵守项目互斥。
2. 用 [派工及报告模板](references/task-and-report-templates.md) 下放编码、自测、证据自检和 MR 维护。报告包含真实命令、失败/修复/复跑、源码与测试绑定、入口及限制；不把局部通过包装成整体质量通过。
3. 用 [交付委托协议](references/delivery-delegation.md) 记录实际用户授权、唯一交付者、作者范围/现有消息目标及顺序。完成/受阻直接交付者 receive/drain，原生或已授权既有工作 agent App thread 按实测能力声明；发送接受、对方确认、最终交付分开。每次重试/消费再验当前 scope/recipient，不让旧缓冲越权；每次就绪/等待/接受/门禁再验最终消息来源，不能只验证报告和握手。身份/指纹核验后才占 canonical；不兼容报告保留原字节并 needs_reconcile，不猜元数据或改 passed。旧 payload 不伪改成已转交，缺文件/旧修订/失效证据不得就绪。
4. 用户一次处理一个 atomic human item。active 不自动插队；用户指定的下一项优先，其次解阻澄清/决策、经审核的外部资料协助和就绪验收同级 FIFO。`next` 给出一项；递给用户才 `wait`；`close` 后立即衔接返回的下一项。资料协助是请求源码/说明等外部材料，不等于业务语义决策；二者的技术依据在每次使用前复核。用户要求继续技术排查时用原子 `redispatch`，同 worker 继续原范围，不把反馈当语义确认或新权限。
5. **交付侧每次收尾必须 `closeout` / `reconcile`**：消费已收回执，核对执行终态/注册报告/blocked 后续责任和双向通路，再以同一 revision 检查。`technical_owner` 指向交付者，常规技术阶段 `notify_main=null`；仅用户事项、整批完成或重要例外回主会话。主会话不再逐项收原始技术回执，可读同账本摘要；准备结束仍检查已到本会话的用户事项和交付汇总。active 不插队，无 active 有 eligible 递一项，否则用工具公开进度说明阶段/事实/下一步、排队/受阻/外部等待/待整合及部署；零任务明确说明。新交付或证据变化必须对账，过期投影不作精确当前计数。单独 `check` 不证明宿主消息覆盖。
6. 代码需求每需求一个 MR，只对齐最新 main，不提前整合或等待其它未合任务。功能接受后原作者维护同一 MR，交付者独审 source/main/源 CI/证据，按主会话授权顺序串行最终合 main；落后或失败直接退回原作者同步重测再送审。同事 MR 同样不代修。只读任务沿用已确认类型和合法成果核验入口，不制造 MR/CI。发布独立冻结 SHA、制品、范围及顺序，后续 main 新 MR 不进入该发布；未选任务合 main 也不自动获部署权。工具只提供离线门禁及显式临时本地裸库 CAS，**不执行真实 GitLab/tag/部署，不保证远端无竞态**。见 [合并门禁](references/merge-gate.md) 与交付委托协议。

恢复先 `show`、`summary`，再做一次对账；不重建空账本，不删去重或历史。写锁冲突直接报错，不自动抢锁；损坏状态先保全再恢复。v1 只对副本迁移至新路径，保留旧历史和权限限制；见状态协议。

用 `describe` 在同账本登记公开标题、范围明确的已完成事实和业务根任务归属，作者/自测/独立复核只计一个业务需求。用 `queue` 记录未派发/等待资源，实际 `start`/`redispatch` 才占配置的 worker_capacity；不能将排队报成正在开发。局部 UI 接受不代替整体质量接受。完成报告展示字段先校验/只读适配再占 canonical，保留原字节和转换来源；已消费旧事件用 refresh-presentation，已发生的当前修订整体验收可用有证据的 record-acceptance 恢复，二者不伪造作者新修订。具体命令及限制见状态协议。

## 验证与能力边界

运行 `python -B -m unittest discover -s scripts -p "test_*.py" -v`；`scripts/demo.py --output ABSOLUTE_NEW_DIRECTORY` 提供陌生项目的进程演练。真实宿主的独立 worker 验收步骤及事件桥接最小方案见 [平台边界与行为验收](references/platform-boundary.md)。进程 fixture 不是原生 agent 送达证明；Stop 是有界续跑提醒，不是阻止或撤回 final 的硬拦截。本 skill 不安装 hook/plugin，不运行 daemon、cron 或定时轮询，不保证宿主闲置自动唤醒。

完整测试包含新一次性仓库 init/commit/ref-CAS；仅在当前授权允许的临时范围运行，不触碰真实项目或 push。范围不允许时明确列出未执行项，不能沿用历史通过代称本次新源码完整通过。

任务类型必须明确：旧任务和缺省类型保守按 code；代码任务经开发自测、验收、集成审核、合入目标 main 并核对后才完成。新只读分析由主会话处理，`prepare` 拒绝新建 read_only 开发者。已有 read_only 历史任务继续保留冻结输入及合法完成协议，交付者通过 `complete_read_only` 核当前修订成果，不制造 MR/CI；明确 user_required 的仍须真实用户接受。类型、验收方式和确认授权不能变更来绕门禁。见[历史只读任务协议](references/read-only-lifecycle-design.md)。

任务完成前保留 agent 上下文，不把 idle/报告 completed 当 closed，不假定记忆可无损恢复。完成后先保全提交号（代码任务）、决策、验收和最小复现/未入库证据及必要知识，再按具体授权回收登记的专属 agent 名额、进程、工作树、临时库和验收环境。共享引用未解除、受保护、活动工作/后代或其它任务实际依赖的资源不回收；尚未部署本身不要求保留旧开发环境。task_completed 与 cleanup_completed 分开，失败 pending_cleanup 不丢任务，未知先核实际效果不重发。后续 bug 从最新 main 新任务关联旧记录；部署另用冻结提交/制品。本组件不实际清理真实项目；回调仅在新具体范围授权内启用。

正常新代码任务使用同插件的 `ResourceBridge.prepare_development/create_worktree`：先核对 CORE cleanup_root 与 RESOURCE cleanup_roots，再实际创建和登记工作树；原 launch/observed 绑定同事务登记实际作者。按需临时目录、库、文件和有限受管进程也通过桥接创建登记；没有创建不填身份，基础 prepare 返回未闭环且登记不全不能清理完成。合目标 main 核验后用 `Runtime.preserve_task` 外部保全当前交付及引用证据，再用原 reclaim_development 清理。保全与确认清理记录绑定后，report_for 可继续核验已经合法删除的临时源，不改原报告或继承旧通过。无宿主能力、创建/关闭未知保持责任和待核验；不扫描补登记历史资源。见[新任务资源入口](references/core-runtime.md#新任务资源入口)。
